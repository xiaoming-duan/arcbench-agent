# UI 契约提取

> 从**自然语言需求正文**提取结构化的 UI 契约：页面上有什么、可访问名是什么、怎么校验。

**形态**：Skill（无外部依赖，可独立使用）
**验证状态**：✅ **真实语料实测** —— 覆盖率 **70.7%**（468 个叶子需求 / 6 个真实应用），精确率 **90.8%**（324/357）

---

## 何时用它

满足**任一**条件时：

- 需求里出现页面 / 表单 / 按钮 / 列表 / 表格 / 弹窗等 UI 元素
- 需求要求「某元素的**可访问名**等于 X」
- 需求含**否定式** UI 要求（「A 的数据**不得**出现在 B 中」）
- 你要为 UI 需求写 E2E 测试，但不确定该测哪些元素

**不适用**：纯后端 API 需求（用 `cross_module_calls` 那套契约）。

---

## 它解决什么

编排层只知道「做注册功能」，无法回答「页面上应该有什么、可访问名该叫什么」。

而可访问名是**可测的** —— 它可以直接映射到 `getByRole` / `getByLabel`。
**把开放式生成变成约束式填空题。**

---

## 输出形状

```yaml
ui_contracts:
  - page: "/(实现自定义：工作簿首页)"     # 需求说"入口格式实现自定义"时就照实写
    title: "Workbooks"
    elements:
      - id: last-updated
        type: text                        # text|password|checkbox|button|link|list|grid|tabs|table|...
        label: "Last updated:"            # ← 可访问名，直接映射 getByLabel
        validation: "每条记录都显示 'Last updated: <值>'"
        error_messages: {format: "..."}   # 可选
        initial: unchecked                # 可选
    error_display: "多个错误同时显示，每条在对应字段旁"
    state_preservation: "失败时保留 username 和 email"
    invariants:                           # ★ 否定式/条件式要求写这里
      - "**另一工作簿的数据不得出现在当前网格中**"
```

### 三个字段的用法要点

| 字段 | 什么时候用 | 注意 |
|---|---|---|
| `label` | 需求原文给了可见文本或可访问名 | **逐字照抄**。占位符（如 `<workbook name>`）原样保留 —— 它是**运行时**才确定的可访问名 |
| `invariants` | 要求是「某种情况**不得发生**」 | 元素清单表达不了这类要求，必须单列 |
| `page` | 需求说「实现自定义」 | **照实写成占位符**，不要替它编一个 URL |

## 提取规则（正则优先 + LLM 兜底）

```
① 正则抓**明确模式** —— 成本低、可复现、误报少
     "accessible name is X" / "可访问名为 X"
     "displays \"X\"" / "显示 \"X\""
     "button labeled X" / "按钮 X"
② LLM 兜底 —— 只处理正则没抓到的部分
③ 合并去重，保留来源（哪条是正则、哪条是模型给的）
```

**为什么正则优先**：准确率是可测的，而正则的行为**确定且可复现**。
LLM 兜底的产出应可追溯到具体句子，便于人工复核。

---

## 口径（**引用准确率时必须一起给出**）

| 指标 | 实测 | 阈值 | 定义 |
|---|---|---|---|
| 覆盖率 | **70.7%** | ≥ 60% | 分母是**叶子需求**；分子是其中提取出至少一个元素的需求 |
| 精确率 | **90.8%** | ≥ 85% | 提取出的可访问名中，有多少**真的出现在平台基准测试 / helpers** 里 |

**两个限定**：

1. **分母是叶子需求**。用**全部**需求算得 **51.7%** —— 容器节点本就不该有 UI 契约。
   不写明口径，两个数字的差异会被误读为矛盾。
2. **精确率是代理指标；召回率未测**。真实 helpers 大量用 role + 正则定位，
   召回率无法可靠测量，故只断言精确率。

单应用覆盖率下限：12306 85% / bookstack 90% / ctrip 55% / keep 90% / prestashop 30% / stackoverflow 50%。

---

## 一个方向对齐检查（不要删）

```
真实 helpers 的定位方式以 getByRole 为主
```

**若这一点不成立，「按可访问名判覆盖」的整个方向就是错的。**
故有一条断言专门钉住它 —— 它是**前提**，不是细节。

---

## 与其它组件的关系

| 组件 | 关系 |
|---|---|
| 契约冻结 | 并行：`cross_module_calls` 管**模块间 API**，`ui_contracts` 管**页面上有什么** |
| UI 门禁 | 下游：门禁按本 Skill 的产出判定「测试是否覆盖了这些元素」 |
| E2E 测试生成 | 下游：测试生成按本产出决定「该断言什么」 |

**未声明 `ui_contracts` 的需求**：不生成、不校验，行为逐位不变（可选字段语义）。
