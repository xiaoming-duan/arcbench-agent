# ARCHITECTURE.md —— 治理层设计哲学

> **一句话**：把 AI 软件生产中的「开放式生成」变成「约束式填空」，
> 并让每个约束**不可绕过、可验证、可观测**。

本文件写给 DSH 的集成决策者：**为什么这样设计、边界在哪、哪些已验证、哪些没有。**

---

## 一、定位：为什么是「治理层」而不是「又一个编排器」

现有 DSH 编排插件（`dsh-ai-team` / `dsh-engineering-control-plane`）强在
**任务拆解、角色路由、多 Agent 协作**。本内核不与之竞争 —— 它补的是另一层：

```
编排层（DSH 现有）      ← 做什么、谁来做、怎么分工
    ↓
治理层（本内核）        ← 什么算做完、凭什么信、证据在哪
    ↓
执行层（DSH 现有）      ← 代码生成、测试执行
```

**判断依据**：编排层的产物是「任务被分配给谁」；
治理层的产物是「一个**可被质疑**的通过/不通过结论，以及支撑它的一整套证据」。

两者正交：编排层无法回答「这个 done 是不是假的」，
治理层无法回答「下一个该做哪个」。

### 一句话概括本层的职责

> **不让"看起来完成"通过。**

实测的四种"看起来完成"：

| 形态 | 实测例子 |
|---|---|
| 报告不完整却判通过 | 一次部分报告（2/6 个需求）被打成「全链通过」 |
| 测试通过但没真集成 | REQ-11 的测试全过，实现却 **0 条 import** 上游 |
| 合同被改但仍按它验收 | 合同写入后被修改，门禁却仍以它为基准 |
| 环境错误冒充实现失败 | 一次 DNS 失败让需求连设计都没做完，却记成需求 FAILED |

**这四种都不是"生成得不好"，而是"治理失效"。** 本层的全部设计都针对它们。

## 二、三个面（领域模型）

治理逻辑天然分成三种关注点。把它们混在一起是实测中最常见的混乱源：

| 面 | 回答的问题 | 本层的实现 |
|---|---|---|
| **控制面** | 这一轮该做什么、花多少预算、何时停 | 编排循环、分类型重试预算、上游失败传播 |
| **正确面** | 什么算对、凭什么信 | 五道门禁、契约冻结、测试审计、判据双向验证 |
| **数据面** | 事实存在哪、怎么追溯 | 需求模型、追溯表、事件流、**预算账本** |

**为什么分面是必要的**（不是审美）：实测中曾把「门禁位置」放在「测试门禁的下游」，
于是**测试不过的需求永不检查依赖** —— 一个纯执行顺序问题，
却导致一整个失败类别被系统性漏检。分面让「谁在谁的上下游」变得可见。

## 三、六条设计原则

### 原则 1：约束优先于提示

**提示词约束不住模型 —— 这条被两次实测确认。**

- REQ-11 拿到 **3 次** 依赖归因提示 + 1 次阻断理由，仍未真实 import 上游
- 契约最初只注入提示词，模型可以忽略

**做法**：把关键约束**落成制品 + 门禁**，而不是留在提示里。

```
需求 YAML（人写的声明）
    │  编译前生成
    ▼
.arc/contracts/<req>.yaml   ← frozen: true，0444 只读 + sha256 侧车
    │  提示词**只读冻结件**
    ▼
模型产出的实现 / 测试
    │  门禁校验
    ▼
一致 -> 放行 ; 缺失/篡改/漂移 -> 阻断
```

### 原则 2：不可绕过，而非"请不要"

权限位（`0444`）只是**纵深防御**，不是安全边界 —— 同用户可 `chmod` 回来。
**真正的保证是哈希校验**，它无法绕过。

两路哈希互补（**这是必需的，不是冗余**）：

| 层 | 覆盖范围 | 为什么需要 |
|---|---|---|
| 内嵌 `integrity.sha256` | **正文**（排除 `hash`/`integrity` 自指字段） | **可移植**：合同单独拿走也能自证 |
| 侧车 `.sha256` | **完整文件字节** | **权威**：连「只改了 integrity 字段」也能发现 |

**自指无解**：哈希写进文件后再算哈希，值就变了。所以内嵌字段只能覆盖正文。

**关键实现纪律**：生成与校验**必须共用同一个 `hash_of_body()`** ——
两边各写一套口径是这类校验最经典的失效方式（生成时算 A、校验时算 B，于是永远不等或永远相等）。

### 原则 3：错误要分类，预算要分账

统一的 `max_retries` 有一个致命缺陷：**环境错误会吃掉实现预算**。

实测：一次 DNS 失败（`[Errno -3] name resolution`）让需求连设计都没做完 ——
那与模型能力无关，却记为需求失败。

```
RETRY_BUDGET = {
    "TEST_FAILED": 3,
    "DEPENDENCY_NOT_USED": 3,
    "CONTRACT_MISMATCH": 2,
    "CONTRACT_MISSING": 1,
    "CONTRACT_TAMPERED": 1,
    "TEST_BROKEN": 2,
    "WEAK_TEST": 2,
    "ENVIRONMENT": 1,
}
```

- 计费键是**信号**（不是粗粒度类别）—— 合同问题改实现修不好，只给 1 次
- **每类独立计数**，互不挤占
- 表外信号回退到四类兜底，不会"没预算可用"
- 未知信号保守归 `implementation`（预算最大）—— 宁可多给一次机会

**实测证据**：某次运行 REQ-11 共尝试 **7 次**，旧统一预算（3）下不可能到 7。
且 `DEPENDENCY_NOT_USED` 花费 4 > 预算 3 → 正确耗尽并阻断。

### 原则 4：五道门禁，不短路合取

```
combined_ok = dep_ok and mock_ok and bypass_ok and contract_ok and ui_ok
```

| 门 | 判定对象 |
|---|---|
| 依赖使用 | 声明了依赖就必须**真实调用**上游（防模块层空转） |
| mock | 测试不得 mock 未声明的上游（防测试层空转） |
| 注入旁路 | 实现不得用形参守卫绕过上游 |
| 契约 | 调用签名符合契约；合同未被篡改 / 未漂移 |
| UI | E2E 存在、RED 有效、元素覆盖、错误消息一致 |

**"不短路"是刻意的**：任一门禁为假都不放行，且**全部门都要被求值** ——
否则被跳过的门禁结果不会被使用，也就不会被发现。

**门禁位置本身也是被测对象**：依赖门禁原先位于 `if outcome.passed:` 之内 ——
测试不过就永不审计。而"测试过不去"**恰恰最可能有依赖问题**。
修法是一行位置移动，但它影响的是一整类漏检。

### 原则 5：机制工作 ≠ 可观测

实测 bug：分类预算**机制在正确工作**（REQ-11 确实消费了 4+3 次），
但账本被门禁段的 `result.gate_audits = {...}` **整体覆盖**，
于是报告里 6 个需求的账本**全部丢失**。

**结论**：没有可观测性时，正确工作的机制与未工作的机制**在报告上不可区分**。

因此：
- 每道门禁的结论进 `gate_audits`
- 分类型预算的 `spent / left / exhausted / history` 进报告
- 元素覆盖映射 / 错误消息覆盖映射进报告
- 报告**完整性**被断言（`reported == requirements_total`）

### 原则 6：验证器自身也是被测对象

**这是本内核最核心的一条，也是踩坑最多的一条。**

七次同类自伤的共同结构：

> **判据/夹具不满足自身前提，看起来像被测对象正常。**

| 次序 | 事件 | 判据错在哪 |
|---|---|---|
| 1 | 断言匹配裸子串 | 命中了自己注释里引用的同一串文字 → 正确的修复看起来是坏的 |
| 2 | fixture 转义过度 | 字面 `\n` 让整段变一行 → 夹具坏了却像被测对象有 bug |
| 3 | 元断言误导输出 | `detail` 无论对错都打印，写成失败语 |
| 4 | 提示词校验 | 整串相等 vs 片段存在性（子节点本来就多一行） |
| 5 | 元测试自己 | `dict` 的 `in` 是**查键**，不是子串 |
| 6 | 快照路径 | 用了错误的路径（零匹配） |
| 7 | fixture SPEC 截断 | **篡改是空操作**，哈希不变 → 断言假绿 |

**两条落地机制**（不是纪律，是可执行的东西）：

- **判据双向验证**：每个断言必须同时给出正确样本（证明不误报）与错误样本（证明能拦住）。
  框架还会识别三种坏判据：**恒真**（漏检）/ **恒假**（噪音）/ **反向**（误报）。
- **修改型夹具前提断言**：记录改前 → 执行修改 → **断言确实不同** → 才断言被测对象。

第 7 次的价值：它把该模式**从"靠注意"变成"可检测"**。

## 四、可移植的最小内核

整个工厂是重的。真正**独特且有验证支撑**的是下面三项 ——
按依赖排序，最轻量优先：

| 模块 | 形态 | 依赖 | 独特之处 |
|---|---|---|---|
| **1. UI 契约提取** | SKILL.md | 无 | 从自然语言需求提取元素清单 + 可访问名规则 |
| **2. 契约冻结** | Tool Plugin | 无 | 合同不可篡改、可自证、三态判定 |
| **3. 分类型重试预算** | Agent Loop Plugin | DSH Agent Loop 接口 | 环境错误不占实现预算 |

**为什么这三项**：它们各自回答一个**编排层无法回答**的问题：

1. 「页面上应该有什么」← 编排层只知道"做注册功能"
2. 「验收依据有没有被改过」← 编排层只传合同，不管合同完整性
3. 「这次失败该不该重试、花谁的预算」← 编排层只有统一重试

### 关于那两个准确率数字 —— **已复现，可引用**

**先记一次我自己的纠错**：初版本文档把这两个数字标为「来源不明」，理由是
「工作区里找不到测量脚本」。**这个判断是错的** —— 我用 `grep 70.7` 时
把它当成了普通数字，而实际来源是一套完整的模块与测试：

```
factory/uicontract.py                    294 行（提取实现）
tests/test_ui_contract_extraction.py     22 项断言（含真实语料）
.probe-upstream/arc-bench/webapp/        真实语料（6 个应用）
```

**本工作区实测复现结果**（口径：**叶子需求**，即容器节点不计入分母）：

| 应用 | 叶子需求 | 命中 | 覆盖率 | 下限 |
|---|---|---|---|---|
| 12306 | 117 | 109 | 93.2% | 85% ✅ |
| bookstack | 34 | 33 | 97.1% | 90% ✅ |
| ctrip | 133 | 89 | 66.9% | 55% ✅ |
| keep | 32 | 31 | 96.9% | 90% ✅ |
| prestashop | 86 | 31 | 36.0% | 30% ✅ |
| stackoverflow | 66 | 38 | 57.6% | 50% ✅ |
| **合计** | **468** | **331** | **70.7%** | 60% |

**精确率**：324/357 = **90.8%**（阈值 85%）。
定义：提取出的可访问名里，有多少**真的出现在平台基准测试 / helpers** 中 ——
这是**精确率代理指标**（名字被平台真实使用 → 不是凭空造的）。

**两个必须注明的口径限定**：

1. **分母是叶子需求**。用**全部**需求算会得到 **51.7%** —— 容器节点本就不该有 UI 契约。
   引用该数字时**必须写明口径**，否则与 51.7% 的差异无法解释。
2. **精确率是代理指标，召回率未测**。真实 helpers 大量用 role + 正则定位，
   召回率无法可靠测量，故只断言精确率。

**结论**：该模块的准确率**有实测支撑，可以引用**（连同口径）。

## 六、整体通过率的诚实表述

6 次 closure6 真实运行（每次 6 个需求）：

| 运行 | 结果 | token | 网关重试 | 配置 |
|---|---|---|---|---|
| run1 | **6/6** | 147,716 | 0 | 契约注入 |
| run2 | 2/6 | 84,388 | 0 | 基线 |
| run3 | **6/6** | 144,336 | 0 | 基线 |
| run4 | 4/6 | 123,955 | 0 | 基线 |
| cf3 | **6/6** | 190,244 | 0 | 契约冻结 |
| p0v | 4/6 | 146,874 | 0 | +分类型预算 |

**全链通过率 3/6。**

**可以说**：「存在使全链 6/6 通过的配置」（3 次实测）。
**不可以说**：「全链通过率 100%」或「契约冻结提升了通过率」——
后者是**因果主张**，需要对照实验，而**样本量与配置差异都不支持**。

**另一个必须注明的限定**：cf3 与 p0v 的 `llm.py` 与 run1–4 **差 163 行**（实测：`diff` 口径；此前记为 110 是在**前向同步之前**测的）
（配额终局判定 / 两后端重试口径统一）。故**跨运行的通过率不可直接对比归因**。

## 七、明确不做

```
不替代 DSH 现有编排插件 —— 作为治理层嵌入
不推倒重来 —— 移植，不重写
不移植未验证组件 —— 未验证的标注「合成验证」，真实运行后再升级
不维护整个工厂 —— 只发布独立模块
不声称未测量的指标 —— 也不把「找不到来源」当成结论（见 LESSONS 纪律 8）
```

## 八、集成后的形态

```
DSH 编排层
    │  任务拆解 → 角色路由
    ▼
┌─────────────────────────────────────┐
│  dsh-governance-kit（本层）          │
│                                     │
│  skill  ui-contract-extraction      │  ← 从需求正文提取 UI 契约
│  tool   freeze_contract             │  ← 写只读合同 + sha256
│  tool   verify_contract             │  ← 三态判定
│  loop   retry-budget                │  ← 分类型预算（需 Agent Loop 接口）
│  prov   audit                       │  ← 可观测性（后续）
│  intr   五道门禁                     │  ← 整合成本最高（后续）
└─────────────────────────────────────┘
    │  通过/不通过 + 证据
    ▼
DSH 执行层
```

**第一版只给 1 + 2**（独立、无依赖）。验证 DSH 接口后再做 3+。
