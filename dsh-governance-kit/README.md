## 一句话

> **不让"看起来完成"通过。**

实测过的四种"看起来完成"：

| 形态 | 实测例子 |
|---|---|
| 报告不完整却判通过 | 2/6 的部分报告被打成「全链通过」 |
| 测试通过但没真集成 | 测试全过，实现却 **0 条 import** 上游 |
| 合同被改但仍按它验收 | 合同被修改，门禁仍以它为基准 |
| 环境错误冒充实现失败 | 一次 DNS 失败让需求连设计都没做完，却记为需求 FAILED |

## 建议的集成顺序

```
1. UI 契约提取 Skill          独立、最轻、有实测准确率
2. 契约冻结 Tool Plugin       独立、核心治理、真实运行验证
3. 分类型重试预算 Agent Loop   依赖 DSH Agent Loop 接口
4. 审计 Provider              可观测性
5. 五道门禁 Interceptor        整合成本最高
```

**先给 1 + 2**，验证 DSH 接口后再做 3+。

## 通过率的诚实表述

6 次 closure6 真实运行（每次 6 需求），**全链通过 3/6**：

| 运行 | 结果 | token | 网关重试 | 配置 |
|---|---|---|---|---|
| run1 | **6/6** | 147,716 | 0 | 契约注入 |
| run2 | 2/6 | 84,388 | 0 | 基线 |
| run3 | **6/6** | 144,336 | 0 | 基线 |
| run4 | 4/6 | 123,955 | 0 | 基线 |
| cf3 | **6/6** | 190,244 | 0 | 契约冻结 |
| p0v | 4/6 | 146,874 | 0 | +分类型预算 |

**可以说**：「存在使全链 6/6 通过的配置」（3 次实测）。
**不可以说**：「通过率 100%」或「契约冻结提升了通过率」—— 后者是**因果主张**，
需要对照实验，而样本量与配置差异都不支持。

**另一个限定**：cf3 / p0v 的 `llm.py` 与 run1–4 **差 163 行**，
故**跨运行的通过率不可直接对比归因**。
