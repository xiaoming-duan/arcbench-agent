# LESSONS.md —— 已知纪律

> 这些不是"最佳实践"，是**踩过的坑**。
> 每条都附**真实事故**与**可执行的防范** —— 只有事故没有防范的叫抱怨。

---

## 纪律 1：判据双向验证

> **写断言前先问：这个判据在正确实现上会通过吗？在错误实现上会失败吗？**
> **如果两个答案都是「不确定」，判据需要重写。**

### 为什么

七次同类自伤的共同结构：

> **判据/夹具不满足自身前提，看起来像被测对象正常。**

| 次序 | 事件 | 判据错在哪 |
|---|---|---|
| 1 | 断言匹配裸子串 | 命中了自己注释里引用的同一串文字 |
| 2 | fixture 转义过度 | 字面 `\n` 让整段变一行 |
| 3 | 元断言误导输出 | `detail` 无论对错都打印，写成失败语 |
| 4 | 提示词校验 | 整串相等 vs 片段存在性 |
| 5 | **元测试自己** | `dict` 的 `in` 是**查键**，不是子串 |
| 6 | 快照路径 | 用了错误的路径（零匹配） |
| 7 | fixture SPEC 截断 | **篡改是空操作**，哈希不变 → 断言假绿 |

**第 1 次最危险**：它让**正确的修复看起来是坏的** ——
若无独立复核，可能把正确的修复回滚掉。

**第 5 次最讽刺**：为「判据正确性」写的元测试，自己用错了判据。

### 可执行的防范

```python
@criterion("T36 审计在 if outcome.passed 之前",
           valid=<正确样本>, invalid=<错误样本>)
```

框架识别三种**坏判据**：

| 坏判据 | 症状 | 危害 |
|---|---|---|
| 恒真 | 两个样本都过 | **漏检** |
| 恒假 | 两个样本都败 | 噪音，拦不住任何东西 |
| 反向 | 正确样本败、错误样本过 | **误报** |

**框架自身也被双向验证**：坏判据必须被判为无效，好判据必须被判为有效。

### 落地口径

> 任何新增/修改判据的提交，必须同时给出 ① 正确样本 ② 错误样本。
> **缺任一个的判据视为「未验证」。**

**只做单向是常见的漏洞来源**：只验证"错误样本被拦住"会漏掉误报，
只验证"正确样本通过"会漏掉漏检。

## 纪律 2：修改型夹具的前提断言

> **任何「修改型」夹具必须有前提断言，证明修改真的生效。**

### 真实事故（第 7 次）

完整性校验的夹具里，SPEC 只声明了 **1 条**调用，
而"篡改"用 `cross_module_calls[:1]` 截断 —— **截断是空操作**，
文件的字节没有变化，于是哈希仍然匹配，门禁判 `ok=True`。

断言本该报 `CONTRACT_TAMPERED`，却**假绿**。

### 可执行的防范

```python
before = p.read_bytes()
tamper(p, lambda d: d.__setitem__("cross_module_calls", d["cross_module_calls"][:1]))
# ★ 前提断言：修改必须真的生效，否则后续断言毫无意义
assert p.read_bytes() != before, (
    "篡改是空操作（fixture 的截断没改到任何东西）—— 断言前提不成立，会得到一个假绿"
)
```

### 通用形式

```
修改型夹具（tamper / patch / rewrite / truncate / rename …）
  → 先记录修改前的可观测状态
  → 执行修改
  → 断言修改后的状态**确实不同**
  → 然后才断言被测对象的行为
```

**缺这一步时，夹具失效与被测对象正常在结果上不可区分** ——
这正是七次事故的共同形态。

**额外实例**（同一次工作中）：一个「去掉元素引用」的夹具只替换了 `getByTestId('grid')`，
却留着 `getByLabel('Grid')` —— 元素**仍被 label 覆盖**，断言前提不成立。
前提断言当场报红。

## 纪律 3：等价不等于忠实

> **逐行实现不得用代数等价改写。**

### 为什么

治理代码里的判定往往是**规格的一部分**，不是"随便怎么写"的逻辑。
把 `spent < budget` 改成 `spent <= budget` 在数学上只差一个边界，
但在语义上是「重试 0 次」与「重试 1 次」的差别。

### 真实事故

预算语义初版写成 `spent < budget`，于是 `budget=1` 的环境错误在**首轮就判死** ——
「重试 1 次」变成「重试 0 次」。**被现有断言 T35a 抓出。**

**"看起来等价"的改写会悄悄改变规格。** 要改语义就改规格并改断言。

## 纪律 4：禁止跨 worktree 用 `cp`

> **不得在 worktree 之间用 `cp` 同步文件。用 `git cherry-pick` / `git merge`。**

### 真实事故（两次）

用 `cp` 在 worktree 之间**按文件**同步，把另一条工作流的文件复制过来 ——
它们引用当前分支**不存在的符号**：

```
把主树的 loop.py / pipeline.py / test_gates.py 复制进分支
  -> 它们引用 ModelQuotaExhaustedError / _is_quota_exhausted
  -> 而分支的 llm.py 是重构前版本，没有这两个符号
  -> ImportError
```

| 次 | 波及 | 后果 |
|---|---|---|
| 1 | **四个提交均不可导入** | 分支一路「绿色」通过报告，因为检查工具一直在**主树**跑 |
| 2 | 分支 3 类断言失败 | 补跑前才发现 |

### 为什么按文件 `cp` 必然出问题

> **按文件挑着 `cp`，必然产生「A 模块新版 + B 模块旧版」的半新半旧状态。**
> 而 `import` 是最先断裂的地方 —— 新模块引用了旧模块里还不存在的符号。

**同步的单位是提交，不是文件。** `git cherry-pick` / `git rebase` / `git merge`
保证整体一致性，且留下可追溯的记录。

### 正确做法

```bash
git cherry-pick <sha>          # 取某个提交的整体改动
git merge <branch>             # 取整个分支的最新状态
```

若确实只要一个文件，也应**说明理由并单独提交**，而不是批量 `cp`。

### 守卫的角色

`import 冒烟守卫`**两次都立刻抓到了污染** —— 守卫有效。
但它是**事后发现**，不是事前阻止。**禁止 `cp` 是事前阻止。**
两者都要有：事前靠纪律，事后靠守卫。

## 纪律 5：验证器自身也是被测对象

> **门禁、判据、夹具、度量函数都需独立验证。**

### 为什么

**四次形态不同的"验证器失效"，每次都伪装成正常：**

| # | 验证器失效的形态 | 伪装成 |
|---|---|---|
| 1 | 报告完整性未检查 | 2/6 的部分报告 → 「全链通过」 |
| 2 | 门禁位置在测试门禁下游 | `dependency_violations=0` → 「依赖用对了」（实为**未被评估**） |
| 3 | 冻结合同读路径因 parent 链失效 → 静默回退 | 提示词里**有**合同内容 → 「冻结生效了」（实为内存声明） |
| 4 | 分类预算账本被门禁段整体覆盖 | 报告完整、状态 FAILED → 「预算没生效」（实为**机制在正确工作**） |

**共同点：验证器失效时，输出仍然"看起来合理"。**

### 三条可执行的防范

**① 报告完整性断言**

```python
# 不要问「报告里的是否全通过」，要问「报告是否完整」
all_passed = (reported == requirements_total) and all(v == "PASSED" for v in states.values())
```

**② 删除一切静默回退**

读不到权威来源时**报错或阻断**，不要回退到"看起来等价"的次优来源。
回退路径会让"未生效"与"生效"在输出上不可区分。

**③ 机制必须可观测**

> **机制工作 ≠ 可观测。**

实测：分类预算**机制在正确工作**（确实消费了 4+3 次），
但账本被覆盖 → 报告里 6 个需求的账本**全部丢失**。
**没有可观测性时，正确工作的机制与未工作的机制在报告上不可区分。**

## 纪律 6：误报比没有门禁更糟

> **一个会误报的门禁会被关掉，而关掉之后什么保护都没有。**

### 真实事故

UI 门禁的元素匹配最初只认**字面 label**。而某个元素的 label 是
`<workbook name>`（**运行时占位符**，可访问名是动态的工作簿名）——
测试不可能硬编码它，于是被判为"未覆盖"，**误报**。

### 可执行的设计

元素覆盖判定**三级由强到弱**，命中任一即算覆盖：

```
① 元素 id 原样 / 连字符 / 下划线 / 驼峰变体
② 可访问名 label 的**可字面部分**
③ **占位符型 label** → 回退到按**角色**匹配（getByRole('link' / 'button' ...)）
```

**判据设计时优先问「它会不会在正常情况下报红」**，
而不是「它能不能拦住所有错误」。**前者决定它会不会被保留。**

## 纪律 7：环境错误不占实现预算

> **网关 / DNS / 配额失败重试再多也不会成功。**

### 真实事故

一次 DNS 失败（`[Errno -3] name resolution`，连续 2 次）
让需求**连设计都没做完**，却被记为需求 FAILED —— 那与模型能力无关。

### 可执行的做法

```
RETRY_BUDGET = {
  TEST_FAILED: 3, DEPENDENCY_NOT_USED: 3, CONTRACT_MISMATCH: 2,
  CONTRACT_MISSING: 1, CONTRACT_TAMPERED: 1,
  TEST_BROKEN: 2, WEAK_TEST: 2,
  ENVIRONMENT: 1,       # ← 只给 1 次，且独立计数
}
```

**每类独立计数**，环境错误**不挤占**实现预算。

**实测证据**：某次运行需求共尝试 **7 次**（旧统一预算 3 下不可能到 7）。

## 纪律 8：不要用「找不到来源」代替「去找来源」

> **`grep` 一个数字找不到，不等于它没有来源 —— 可能只是我搜错了形态。**

### 真实事故（写这三份文档时发生）

外部提案引用「UI 契约提取：覆盖 70.7% / 精确 90.8%」。
我 `grep 70.7` —— 命中的都是无关的 JSON 数字，于是判定**「来源不明」**并写进文档，
还建议「集成前标注为准确率未测」。

**这个判断是错的。** 实际情况：

```
factory/uicontract.py                    294 行提取实现
tests/test_ui_contract_extraction.py     22 项断言（含真实语料）
.probe-upstream/arc-bench/webapp/        6 个真实应用的需求语料
```

复现结果与提案**逐位吻合**：覆盖 70.7%（468 个叶子需求）/ 精确 90.8%（324/357）。

### 为什么会误判

**两个独立的错误叠加**：

1. **搜错了形态**：`70.7` 在源码里写成 `MIN_TOTAL_COVERAGE = 0.60  # 实测 70.7%` ——
   我搜到了它，但因为我预期的是"测量脚本 + 结果文件"，
   就把源码注释里的数字当成了巧合。
2. **没找对分母**：我用自己的口径（全部需求）算得 **51.7%**，
   与 70.7% 不符，于是更确信"没有来源"。
   而正确口径是**叶子需求**（容器节点本就不该有 UI 契约）。

### 可执行的防范

**声称「无来源」前，必须至少尝试三种检索**：

```
① 数字本身（含百分比与小数两种写法：70.7  /  0.707）
② 指标名（覆盖率 / 精确率 / coverage / precision）
③ 功能名（契约提取 / uicontract / extraction）
```

**并且**：若自己复算出的值与待验证值不符，**先怀疑口径，再怀疑数据** ——
先去找定义（测试里的分母是什么），而不是直接下"数据有问题"的结论。

**这条与纪律 1 同源**：都是**判据（这里是检索判据）不满足自身前提**。
我当时的隐含前提是「来源 = 测量脚本 + 结果文件」，
而实际来源可以是「实现 + 测试 + 语料」这一整套。

## 纪律 9：提交信息不得含反引号

> **反引号在 shell 里是命令替换。用双引号包裹提交信息时，反引号里的内容
> 会被当命令执行 —— 短语被静默吞掉，且没有任何报错。**

### 真实事故（第 2 次同类）

```bash
git commit -m "事后靠 `merge-base --is-ancestor` 检查"
#                    ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^ 被 shell 执行
```

结果提交信息变成：

```
事后靠  检查          <- 少了半个句子。**没有报错，没有警告。**
```

同一提交里另一处：`A `merge --no-ff`（首选…）` -> `A （首选…）`。

### 为什么这次特别值得记

**它损坏的是「历史记录」本身。**

- 代码错了，测试会报红
- 文档数字错了，复核能发现
- **提交信息错了，没有人会去 diff 它** —— 它读起来仍然通顺，只是缺了内容

上一条事故（`f8a2504`「声称同步回主树但同步没发生」）也是**提交信息说假话**。
两次都指向同一件事：**提交信息是唯一没有验证器的产物。**

### 机制（不是纪律）

```bash
.git/hooks/commit-msg     # 拒绝含反引号的提交信息
```

| 手段 | 生效时机 | 局限 |
|---|---|---|
| **hook** | 事前 —— 每次提交都拦 | 仅本仓库（`.git/hooks/` 不入版本库） |
| 本文（纪律 9） | 事后 —— 靠人读到 | 靠记性 |

**hook 是主要的，本文是配套的。** 但 hook 有一个**真实的局限**：
`.git/hooks/` **不随仓库分发** —— 换一台机器、重新 clone，
hook 就没了，而纪律 9 作为文件还在。

> **这本身就是一条教训**：机制若不被版本管理，它的寿命短于纪律。
> 若要让所有人都有这个 hook，需要 `core.hooksPath` 指向仓库内的目录，
> 或写进 CI 检查。**本仓库目前只做了本地 hook —— 这是已知局限。**

### 三种替代写法

```bash
# ① 单引号包裹（反引号在单引号里是普通字符）
git commit -m '含 `反引号` 的信息'

# ② 从文件读取 —— 最稳，推荐
git commit -F .commitmsg

# ③ 用方括号代替反引号
git commit -m '事后靠 [merge-base --is-ancestor] 检查'
```

**注意 hook 的判据是「内容里有没有反引号」，不看它由谁产生** ——
即使你用单引号包裹、内容里确实需要反引号，也会被拒。
这是**刻意的**：提交信息里几乎不需要反引号，拒掉比放过安全。

## 附：这九条纪律的来源

它们不是设计出来的，是**在真实运行中被反复纠正出来的**。
一条纪律若没有对应的事故，就不该写进来 —— 因为无法判断它防范什么。

| 纪律 | 事故次数 | 是否已机制化 |
|---|---|---|
| 1 判据双向验证 | 7 | ✅ 框架（含坏判据识别） |
| 2 修改型夹具前提断言 | 1（第 7 次） | ✅ 已写成通用形式 |
| 3 等价不等于忠实 | 1 | ⚠️ 靠评审 |
| 4 禁止跨 worktree cp | 2 | ✅ 源码级扫描断言 + import 守卫 |
| 5 验证器自身也是被测对象 | 4 | ⚠️ 部分（完整性断言 / 无回退 / 可观测） |
| 6 误报比没有门禁更糟 | 1 | ✅ 三级匹配 |
| 7 环境错误不占实现预算 | 1 | ✅ 分类型预算 |
| 8 不要用「找不到来源」代替「去找来源」 | 1 | ⚠️ 靠检索纪律（三条检索 + 先疑口径） |
| 9 提交信息不得含反引号 | 2 | ⚠️ **部分**：本地 hook 已装，但 `.git/hooks/` 不入版本库 |

**未机制化的三条（3 / 5 / 8）是本套件最薄弱处**，集成时值得优先补。

**纪律 9 是「部分机制化」** —— hook 在本地有效，但它不进版本库，
换机器即失效。**要被版本管理的 hook 才算真正机制化**（`core.hooksPath` 或 CI 检查）。
