============================================================

相对 v8 的变化
------------------------------------------------------------

① 凭据无效（401）与配额耗尽同属**终局故障**，不再逐个需求去撞
   平台日志（2026-10-02 07:19）：
     POST /v1/chat/completions "HTTP/1.1 401 Unauthorized"
     {'code': 'invalid_api_key', 'message': 'unauthorized'}
   （该次为使用者写错 key，非平台问题。）
   401 **不被重试是对的**（当时已如此），但它此前**不会终止整轮** ——
   REQ-1-1-1 撞完 401 后，流水线继续去试 REQ-2-1-1，再撞一次同一堵墙。
   新增 ModelFatalError 基类（「本进程内不可能靠重试或换提示词恢复」），
   ModelQuotaExhaustedError 与 ModelAuthError 都继承它；
   两条后端在重试之前先判凭据（状态码 401 优先、文本兜底）-> 即刻上抛；
   loop 三处 except 与 pipeline 终止条件改捕基类。
   端到端实测：3 个需求 + 401 -> design 只被调用 **1 次**、report.ok=False。

 此前判断的更正（写进标签以免后人再走弯路）
────────────────────────────────────────────────────────────
② **端口不是错配**。v8 那次平台运行里应用起在 **3000**：
     [template-app.stdout] Backend listening at http://127.0.0.1:3000
   而 v8 代码是 `process.env.PORT || ARC_RUNTIME_PORT || 3301` ——
   3000 只能来自平台注入的 PORT。=> **端口由平台控制**。
   v8 里把默认值改成 3301 属无害但**在实际运行中是死代码**；
   保留它（PORT 缺失时更贴近基准的 3301），但不再声称它修好了什么。

③ **frontend 构建很可能是冗余的**。平台 runner 自己会跑
     [frontend-npm-install] / [frontend-npm-build] / [backend-npm-install]
   我们的 ensure_frontend_build 也跑了（日志可见），多花约 3 秒、无害。
   之前那条 "application server exited before becoming ready (code=1)"
   更可能就是**已确证**的 `Cannot find module './routes/branchRoutes'` 崩溃
   （app 真的挂了），那个由实现侧模块图审计针对。
